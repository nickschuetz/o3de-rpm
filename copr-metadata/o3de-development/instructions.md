**Development-branch builds.** This project tracks upstream's `development` branch (the 26.10 line, package `o3de2610`). Builds ship **bundled Qt6 6.11.2** (upstream `development` moved from 6.10.2 to 6.11.2 with o3de/o3de#20085; the 26.10 stabilization line stays on 6.10.2) plus the **21-library system-swap set** from 2610.0-123 (the earlier 17 plus system rapidjson, xxhash, cityhash and libtiff; CentOS Stream 10 keeps the bundled rapidjson, so 20 there). Only Qt6 stays bundled among the migration targets; the system-Qt6 swap is held back pending Option B, see hellaenergy/o3de-stabilization for the why. Refreshed automatically by a weekly Sunday 06:00 UTC cron (`.github/workflows/snapshot-development.yml`), which skips the build when upstream's `development` tip has not moved since the last successful build; packagers can also fire a manual rebuild at any time.

**Release game export works here.** These builds ship the monolithic (release, static) engine permutation alongside the default profile engine, so exporting a project in the release configuration (Project Manager "Export Launcher" with Build Monolithic on, or `o3de export-project ... -cfg release`) links and runs directly against the installed RPM, no source build of the engine required. Since 2610.0-127 the exported release game also quits cleanly. Before that it aborted with "pure virtual method called" at exit, because static tables in the Maestro (cinematics) gem were freed after the engine's memory allocator (upstream code, found 2026-10-22, fixed here by Patch0024 from 2610.0-127; the same fix merged into development as o3de/o3de#20232 on 2026-10-26, so builds of the current development tip get it from upstream).

**For stable releases, use [hellaenergy/o3de](https://copr.fedorainfracloud.org/coprs/hellaenergy/o3de/)**: that channel tracks upstream's `main` branch (where each release is merged + tagged).

**For pre-release validation of the next release line, use [hellaenergy/o3de-stabilization](https://copr.fedorainfracloud.org/coprs/hellaenergy/o3de-stabilization/)**: that channel ships builds from upstream's `stabilization/<release>` branch, closer to release quality, validated continuously.

**For an in-progress migration branch:** a separate dedicated COPR project is created rather than overloading this one (as was done for the Qt6 migration, which has since merged into development). This project (`o3de-development`) is exclusively for the `development` branch so chroot config can stay simple and predictable.

**If you're here looking for development-branch builds:**

    sudo dnf copr enable hellaenergy/o3de-development
    sudo dnf install o3de2610 o3de2610-devel

**CentOS Stream 10:** enable CRB and EPEL 10 before installing. They provide libraries the engine needs (assimp, google-benchmark, libunwind, poly2tri); without them `dnf` stops with "nothing provides" errors for those. COPR's own EPEL setting only applies while building the packages, not on your machine.

    sudo dnf install dnf-plugins-core
    sudo dnf config-manager --set-enabled crb
    sudo dnf install epel-release

Then enable this project with the CentOS Stream repository named explicitly (a plain `dnf copr enable` looks for an `epel-10-x86_64` repository, which this project does not have, and fails):

    sudo dnf copr enable hellaenergy/o3de-development centos-stream-10-x86_64

The `o3de-dependencies` repo auto-enables alongside this one. The package name follows a versioned-major convention (`o3de2610` for the 26.10.x line); multiple O3DE majors can be installed side-by-side at `/opt/O3DE/<version>/`, the same path pattern as upstream's `.deb` and Windows installer (upstream's `.deb` installs one release at a time, because every release has the package name `o3de`).

**Maintainer note on `make copr-development` builds:** because this project tracks `o3de/development` tip, seven of our carry-patches (Patch0001/0002/0004/0005/0007/0008/0012) have upstream equivalents that already merged into development and would fail to apply against the source tree at `%prep` (Patch0004 is the newest, superseded by o3de/o3de#19752 on 2026-06-09). The spec's `o3de_base_2610` macro gates them off (with 0009, the 26.05-only swap gates 0006/0013, and since 2610.0-123 Patch0016, merged upstream as o3de/o3de#19825); `development_snapshot` turns it on, and the Makefile's `copr-development` target sets `--with development_snapshot` automatically at SRPM-build time. The applied set here is 0003, 0010, 0011, 0014, 0015, 0020, 0023 and, since 2610.0-127, 0024. **The bcond set is also configured on the chroots** via `copr-cli edit-chroot --rpmbuild-with '<full set>' hellaenergy/o3de-development/<chroot>` (because `--with` flags don't propagate through COPR's SRPM rebuild). The full set is `development_snapshot qt6 monolithic swap_hook` plus the 21 `system_*` swaps (assimp, cityhash, dxc, expat, freetype, googlebenchmark, libsamplerate, lua, lz4, mcpp, mikkelsen, openexr, png, poly2tri, rapidjson, spirvcross, sqlite, tiff, vulkan_validation_layers, xxhash, zlib; rapidjson not on centos-stream-10, whose EPEL rapidjson is still the 1.1.0 release); `make -s print-copr-with CHANNEL=development CHROOT=<chroot>` prints a chroot's list. The `swap_hook` bcond activates the central system-swap download hook (Patch0014, with Patch0015 for the Vulkan validation layer) that the swaps ride on under `development_snapshot`. Development builds rapidjson, xxhash, cityhash and mikktspace from in-tree providers that win over our Find modules (o3de/o3de#20097), so `%prep` replaces those providers with `sources/fetchcontent-provider-system.cmake` when the swap is on (from 2610.0-123; before that, `system_mikkelsen` had no effect here). The `monolithic` bcond adds a second release-config engine build so a release game export works (promoted from o3de-experimental on 2026-08-03 after end-to-end export validation); it costs roughly +0.7 GB and +1.5 h per build. A `qt6-merge-gate` pre-flight halts the build if upstream `development` has flipped to Qt6 while these chroots do not yet carry the `qt6` bcond.

`o3de2610-devel` is part of the install line above on purpose. It carries the engine's static libraries, and every project build links its launchers against them (`AzGameFramework`, `Launcher.Static`), so Project Manager cannot build a project without it. The main package also Recommends it, but naming it explicitly keeps it installed where weak dependencies are off (containers, Toolbox/distrobox, minimal images, `install_weak_deps=False`).

**Building projects (the toolchain is installed for you):** a normal `sudo dnf install o3de2610` also pulls in everything needed to build a project from source, the compiler and build tools (`clang`, `cmake`, `ninja-build`) plus the `-devel` headers a project links against, declared as weak dependencies (Recommends) so dnf installs them by default while a runtime-only user can opt out. Heads-up for containers and minimal installs: if your environment has weak dependencies turned off, the toolchain is skipped and project builds fail on missing compilers or headers. This is common inside containers, Toolbox, and distrobox, on minimal/server images (which often set `install_weak_deps=False`), or when installing with `--no-install-recommends` / `--setopt=install_weak_deps=False`. Backfill the whole set with `sudo dnf install $(rpm -q --recommends o3de2610 | awk '{print $1}')`, which names the Recommends explicitly. A plain `sudo dnf install o3de2610` will not help here: dnf treats the already-installed package as "nothing to do" and never revisits the skipped weak deps.
